PART 0   THE PROJECT ON ONE PAGE
##########################################################################################

0.1  The problem
----------------
A substation (the building where high-voltage lines meet and are switched) is protected by
devices called relays. Relays talk to each other with short network messages called GOOSE
messages (IEC 61850 standard). "Breaker 3 has opened" is one such message. If an attacker can
forge, insert or replay these messages, they can make a relay open a breaker that should stay
closed, or hide a real fault. So we want a detector: a program that looks at every message
and says which of five things it is:

    Normal        routine heartbeat traffic
    Fault         a real electrical fault (a natural event, not an attack)
    Masquerade    an attacker pretends to be a legitimate device
    Injection     an attacker inserts crafted messages into the stream
    Replay        an attacker re-sends genuine messages that were recorded earlier

The project has two halves.

  HALF 1 (steps 1-4, 6, 8)   Machine learning.  How well can a detector tell these five
                             classes apart, using which evidence, and how honestly can we
                             measure that?
  HALF 2 (steps 5, 7)        Grid design.  Given a set of substation sites, build the
                             transmission network, decide where sensors go, where the
                             detector models live, which links carry the alerts, and do it
                             with graph algorithms (BFS, DFS, Dijkstra, spanning trees, max-
                             flow). Then compare that designed grid with a default one.

The two halves meet in one place: the detector's measured recall (half 1) says how much of an
attack a detector catches, and the graph (half 2) says which substation gets which detector
and whether its alert can still reach someone after parts of the grid fail.

0.2  What the professor asked for
---------------------------------
"Make the smart grid optimized at creation too: build a default non-optimized smart grid and
an optimized created one, check the performance and the security of both, and say the
optimized one is better."

Answer in this project (steps 6 and 7), in three points:
  * SECURITY: the optimized grid is clearly better. On every one of the 10 security measures
    (5 "outcomes" such as how much attack detection survives a failure, 5 "objectives" such as
    single points of failure) it beats both default grids, with 95% intervals that exclude zero.
  * PERFORMANCE: it ties on detection quality and on link load, and it is slightly SLOWER
    (the alert passes through three scoring stages instead of one). On your laptop that costs
    +11.4 ms on a ~460 ms path; on a faster CPU +4.6 ms. Cost is +37% over the naive default and
    about the same as a default given the same money.
  * VERDICT: the overall label comes from a rule fixed in advance (PART 6): "OPTIMIZED BETTER"
    needs zero performance losses, and the allowed latency difference is 10 ms. On the CPU where
    the project was first run the label is OPTIMIZED BETTER; in YOUR run (22:39, 18 Oct) the
    latency difference is 11.4 ms, just over the 10 ms limit, so the label is NOT ESTABLISHED
    even though all 10 security measures win. That is the rule doing its job, not a bug, and
    it is explained in PART 6.6 together with the honest options you have.

PART 1   BACKGROUND YOU NEED
##########################################################################################

1.1  The substation and the messages
------------------------------------
  Substation        building where lines meet; contains breakers (switches), transformers,
                    and protection relays.
  Breaker (CB)      a big switch that opens to cut a line when something goes wrong.
  Relay / IED       "intelligent electronic device": the computer that decides to open a
                    breaker. It also logs why. In the data, the MU*Log columns and any_relay
                    are relay log flags.
  Merging unit (MU) a box that measures voltage and current on the lines (digitising the
                    signals from instrument transformers) and publishes them as numbers on
                    the "process bus". The testbed has four of them: MU1..MU4.
  Phasor            a voltage or current described by size and angle. The data holds angle
                    columns (e.g. MU1VoltageAngleA) and three-phase sums.
  PMU               "phasor measurement unit": a sensor that measures phasors precisely with
                    GPS time. In this project "a PMU at a substation" means a process-bus
                    sensor feed there; it is what step 5 places.
  GOOSE             a fast multicast message that relays use to tell each other events. When
                    nothing happens it is repeated as a heartbeat (about once a second here).
                    It carries two counters:
                      stNum   state number, goes up by 1 whenever the reported state changes
                      sqNum   sequence number, counts repeats of the SAME state and restarts
                              when the state changes
  Process bus vs   the process bus carries raw measurements (voltages, currents) from the
  station bus      MUs; the station bus carries GOOSE events, relay logs and checks between
                    devices. This split is why the columns are grouped in layers (PART 2).

1.2  The attack types, in plain words
-------------------------------------
  Fault        a real short circuit etc. Not an attack, but it also makes breakers trip, so
               a detector must not confuse it with an attack (false alert).
  Masquerade   the attacker sends fake GOOSE messages pretending to be a genuine device, e.g.
               "breaker open!". In the data these mostly carry a breaker-open state_cb=1 but
               NO relay log and a failed consistency check (PART 2.4).
  Injection    crafted extra messages are inserted into the stream; typically their counters
               jump (the data shows big stNum jumps).
  Replay       genuine recorded messages are sent again. Because they ARE genuine copies they
               look like normal traffic, which is why Replay (and Injection) are the hardest.

1.3  Machine-learning terms used throughout
-------------------------------------------
  Feature / label     a feature is one input column; the label is the class to predict.
  Model               XGBoost, a boosted ensemble of decision trees (300 trees, depth 6). If
                      xgboost is not installed the code falls back to scikit-learn's
                      HistGradientBoosting. The setting is frozen in config.MODEL_PARAMS and
                      is the SAME for every comparison, so differences come from the evidence,
                      not from tuning.
  Accuracy            share predicted right. NOT used as a headline here: always answering
                      "Normal" is right 41.6% of the time, so accuracy hides which attack a
                      model misses.
  Recall (per class)  of all messages that truly are class X, what share did we catch?
  Precision           of the messages we called X, what share truly are X?
  F1                  one number from precision and recall (their harmonic mean).
  Macro-F1            F1 computed for each class and then averaged with EQUAL weight, so the
                      41 Fault rows count as much as the 455 Normal rows. This is the main
                      score.
  PR-AUC              area under the precision-recall curve; threshold-free ranking quality.
  False alert         a non-attack message (Normal or Fault) flagged as an attack. Also
                      expressed per day: false alerts per day.
  Threshold           the cut-off on the detector's attack score above which it raises an
                      alert. Lower threshold = more attacks caught and more false alerts.
  Attack coverage     the average of the recalls of the three attack classes at a given
                      threshold: how much of the attack traffic a detector sees.
  Cross-validation    split the data into folds, train on all but one fold, score the held-out
                      fold, repeat. Gives an average and a spread (SD).
  Out-of-fold (OOF)   a score for a message produced by a model that never saw that message's
                      fold. OOF scores are honest; scores from a model's own training data
                      are not.
  Leakage             anything that lets the model "see" the answer at test time. Here the
                      main leak is time: neighbouring messages are near-duplicates, so a
                      random split puts copies of the same message on both sides.
  Blocked CV          cut the recording into contiguous time blocks and hold out WHOLE blocks.
                      Neighbours stay together, so the held-out data is genuinely unseen.
                      (StratifiedGroupKFold in scikit-learn, 20 blocks, 5 folds.)
  Bootstrap           resample the data many times to see how much a number would wobble. Used
                      for 95% confidence intervals. Here the resampling unit is a time BLOCK
                      (a "block bootstrap"), because rows within a block are not independent.
  Paired bootstrap    resample so two things being compared use the same resamples; the
                      difference then has a proper interval.
  Ablation            remove or isolate part of the input (a layer) to see what it contributes.
  Control experiment  a deliberately useless input (the clock alone) to check that the model
                      is not learning the capture timeline instead of the attacks.

1.4  Graph terms used in step 5 and 7
-------------------------------------
  A graph is nodes (substations) joined by edges (transmission lines, which also carry the
  fibre for communications).

  BFS (breadth-first search)   explores outward one hop at a time; gives hop counts and "what
                               is reachable?". Used for failure sweeps: delete the failed
                               nodes, run BFS, see who can still reach a control point.
  DFS (depth-first search)     explores as deep as possible first; used for connected
                               components and, with low-link values, for bridges (Tarjan).
  Dijkstra                     shortest paths by weighted length; here weight = latency in
                               milliseconds.
  Minimum spanning tree (MST)  the cheapest set of edges that connects every node (Kruskal's
                               algorithm: take the cheapest edge that does not close a loop).
                               A tree is "radial": cheap, but every line is a single point of
                               failure.
  Bridge                       an edge whose loss disconnects the graph.
  Cut vertex                   a node whose loss disconnects the graph.
  N-1 secure                   the grid stays connected after losing any ONE line or any ONE
                               substation = no bridges and no cut vertices. In this project
                               N-1 is TOPOLOGICAL only (connectivity); power-flow capacity is
                               not checked (PART 8).
  Menger's theorem / max-flow  the number of independent routes between two nodes equals the
                               smallest number of links (or nodes) whose loss separates them.
                               Computed by max-flow (Edmonds-Karp). "2 independent routes to
                               the control centre" means two disjoint failures are needed to
                               cut a substation off.
  Dominating set               a set of nodes such that every node is in the set or next to
                               one. A PMU sees its own substation and its neighbours, so
                               "observe every substation with the fewest PMUs" is a minimum
                               dominating set (solved exactly by an integer program).
  Zero-injection bus           a junction with no generation and no load; Kirchhoff's current
                               law lets observability spread through it, which saves PMUs.
  k-medoid (PAM) clustering    choose k representative nodes ("hubs") so every node is close
                               (in latency) to one; used to split the grid into zones.
  Blast radius                 the share of the grid exposed if ONE hub or control centre is
                               compromised. A policy cap (25%) forces more zones.
  Lateral movement             an intruder hopping from a compromised node to its neighbours;
                               segmenting the network into zones limits how far it can go.

2.1  Where it comes from and what the files are
-----------------------------------------------
  Source     Kaggle, "Power System Intrusion Dataset" (user sequincozes):
             https://www.kaggle.com/datasets/sequincozes/power-system-intrusion-dataset
  Content    IEC 61850 GOOSE messages captured in a substation testbed that has four merging
             units (MU1..MU4), with the quantities derived from each message.
  Files      dataset/Train.csv   1,094 rows, 54 columns
             dataset/Test.csv    1,094 rows, 54 columns
  Columns    "time"  + 52 feature columns + "class".

  An honest note: the Kaggle page could not be opened from the environment where this code
  was written, and the files carry no documentation. So the descriptions below are what the
  files themselves show (counts, ranges, per-class behaviour, and checks I ran), plus the
  standard meaning of GOOSE and IEC 61850 terms. Where I say "my reading" it is an
  interpretation of column names and values, not the authors' definition.

2.2  One row = one message
--------------------------
Each row is ONE GOOSE message seen on the testbed at one moment. It records:
  * when it arrived ("time", milliseconds from the start of the capture),
  * the protocol counters it carried (sqNum, stnum) and how they changed since the previous
    message (sqDiff, stDiff, timeLastMsg, recentChange),
  * the breaker state it reported (state_cb),
  * the measurements the four merging units reported at that moment (voltage and current
    angles, three-phase sums),
  * check flags (consistency, MU*Cs, Cs) and relay logs (MU*Log, any_relay),
  * the label ("class") assigned by the people who built the dataset.

"time" and "class" are never used as inputs to a model. "time" is only used to order the
rows and to cut the capture into blocks (it is the capture clock: a model given it could learn
WHEN attacks were launched instead of what they look like; experiment E1 includes a control
that proves how little the clock alone is worth: macro-F1 0.17). "class" is the target.

2.3  The 52 feature columns, layer by layer
-------------------------------------------
The project groups the columns into four layers by where in the substation the evidence is
produced (src/modalities.py; the full mapping is written to outputs/step2_view_map.csv).
"station" is not a fifth set of columns: it is goose + consistency + relay together (20
columns), i.e. everything a station-level computer sees WITHOUT the raw phasors.

  LAYER goose (7)  -- protocol state on the station bus
    sqNum         GOOSE sequence number (1..53 in this capture).
    stnum         GOOSE state number (1..100).
    state_cb      circuit-breaker state reported by the message (0 or 1). 1 in 465 of 1094
                  rows.
    sqDiff        sqNum minus the previous message's sqNum (range -52..50).
    stDiff        stnum minus the previous message's stnum (range -81..89).
    timeLastMsg   milliseconds since the previous message of ANY class (0..1001). Normal
                  heartbeats are about 1000 ms apart, but attack messages arrive in between
                  and shorten the gap (median 619 ms for Normal rows, 228-312 ms for attacks).
    recentChange  change in state_cb versus the previous message: -1, 0 or +1.
                  (In Train.csv it equals state_cb minus the previous row's state_cb in 99.1%
                  of rows.)

  LAYER consistency (8)  -- cross-checks computed at the station
    MU1Cs MU2Cs MU3Cs MU4Cs   per-merging-unit consistency flags. Non-zero in only 6, 4, 0
                  and 31 rows. MU3Cs is constant 0 -- the only constant column; it is kept
                  because removing it changes nothing.
    Cs            a combined flag, non-zero in 48 rows.
    consistency   an overall check flag, 1 in 621 rows. My reading: 1 = the message passes the
                  cross-check. It is 1 for 98% of Normal rows and only 6% of Masquerade rows
                  (table in 2.4), which is why it matters so much.
    threePhaseVSum, threePhaseCSum   sums of the three phase voltages / currents. For a healthy
                  balanced system they are near 0 (Kirchhoff residual); large values signal
                  a disturbance or inconsistent numbers.

  LAYER relay (5)  -- protection-relay log flags
    MU1Log MU2Log MU3Log MU4Log   the relay logged an event for that unit (non-zero in 46, 52,
                  33 and 34 rows).
    any_relay     1 if any relay logged (92 rows). It is 0 for every Normal row and 1 for
                  every Fault row: a real fault always shows up in the relay log.

  LAYER process (32)  -- raw merging-unit measurements (the "process bus")
    Per merging unit (8 columns each, 4 units = 32):
      threePhaseV<MU>        voltage magnitude summary (named threePhaseVMU1 .. threePhaseVMU4)
      <MU>VoltageAngleA/B/C  voltage angle on phase A, B, C (degrees, -180..180)
      threePhaseC<MU>        current magnitude summary (threePhaseCurrentMU1,
                             threePhaseCMU2, threePhaseCMU3, threePhaseCMU4)
      <MU>CurrentAngleA/B/C  current angle on phases A, B, C (MU4's are named IED4_iA/B/C)
    Angles take a different value in almost every row (about 1,000 distinct values per 1,094
    rows), so a tree model can use them to MEMORISE a particular message. That is exactly why
    the process view scores 1.000 in Train->Test (the same messages are in both files) and
    only 0.308 under honest blocked CV.

  Counts: 7 + 8 + 5 + 32 = 52.   station = 7 + 8 + 5 = 20.   all = 52.

2.4  The five classes, and what each looks like in the data
------------------------------------------------------------
Class counts (the same in Train.csv and Test.csv):

    Normal 455 (41.6%)   Masquerade 397 (36.3%)   Injection 101 (9.2%)
    Replay 100 (9.1%)    Fault 41 (3.7%)

Always answering "Normal" gives 41.6% accuracy; this is why accuracy is not reported.
Families used in the project: Normal; Natural (= Fault); Attack (= Masquerade, Injection,
Replay).

Per-class profile of the main station-layer columns, computed from Train.csv (share of rows
where the flag is non-zero, or the median value):

                         Normal   Fault  Masquerade  Injection  Replay
    state_cb  (share=1)    0.00    1.00      0.91       0.50      0.12
    any_relay (share=1)    0.00    1.00      0.09       0.07      0.09
    consistency (share=1)  0.98    0.32      0.06       0.50      0.84
    MU1Log / MU2Log        0.00    0.61/0.63 0.04       0.05/0.06 0.02/0.03
    MU3Log / MU4Log        0.00    0.29/0.27 0.04       0.01      0.06/0.05
    recentChange != 0      0.59    0.68      0.71       0.47      0.39
    median timeLastMsg ms  619     293       289        228       312
    median sqNum           9       1         6          17        6
    median stDiff          0       1         1          7         -3

What this says, in plain words (my reading):
  * Normal      quiet: no breaker-open state, no relay log, passes the consistency check, and
                messages arrive about a second apart.
  * Fault       breaker open (state_cb=1 in every row) AND the relay logged it (any_relay=1 in
                every row). sqNum is 1: a new event just started.
  * Masquerade  also reports breaker-open (91%) but the relay did NOT log it (91% have
                any_relay=0) and the consistency check fails (94% have consistency=0). A
                fake trip: it imitates a Fault's breaker state without a relay behind it. That
                is the signature that separates Fault from Masquerade.
  * Injection   the counters jump: median stDiff is 7 (normal traffic: 0), messages arrive
                faster (median gap 228 ms). Consistency and breaker state are mixed (50/50),
                which is why Injection is hard.
  * Replay      the hardest. A replayed message is a genuine old message, so it looks like
                Normal on most columns (consistency 0.84, breaker state 0.12). Only subtle
                timing and counter patterns give it away.

Detector results follow this: Masquerade and Fault are recognised ~93-94% of the time under
honest evaluation, Injection and Replay only ~40% (PART 4, step 3 and E1).

2.5  The capture timeline
-------------------------
  * Length: 476.96 seconds (about 8 minutes). First message at 1.0 s, last at 477.96 s.
  * 1,094 messages -> 2.294 messages per second on average (outputs/step1_profile.json).
  * Normal traffic is a heartbeat: the gap between consecutive Normal messages has a median
    of exactly 1000 ms. Fault and attack messages arrive in between.
  * Median gap between any two consecutive messages 371 ms; 95th percentile 1000 ms.
  * Non-attack rate (Normal + Fault): 496 messages / 476.96 s = 1.04 per second. This number
    converts false-alert RATES into false alerts PER DAY (x86,400 s): one false alert among
    the 496 non-attack messages is already 181 false alerts a day, the "resolution floor" of
    experiment E6.
  * Four merging units contribute to every row. Per-bay quantities in step 5 are the measured
    row divided by 4.

The capture is cut into 20 equal-width time blocks of about 23.9 s each (block 0 starts at
1.0 s, block 19 at 454.4 s). Messages per class in each block:

2.6  How the derived timing columns are computed (verified)
-----------------------------------------------------------
sqDiff, stDiff, timeLastMsg and recentChange are DIFFERENCES between a row and the row before
it in time order. I checked this on Train.csv by re-computing them from the time-ordered rows:

    timeLastMsg  =  time          - previous time        matches in 97.3% of rows
    sqDiff       =  sqNum         - previous sqNum       matches in 97.3% of rows
    stDiff       =  stnum         - previous stnum       matches in 98.6% of rows
    recentChange =  state_cb      - previous state_cb    matches in 99.1% of rows

(The first row has no predecessor; the rest of the mismatches are ties and edge cases I did
not chase.) Consequence: these are not independent measurements of the message; each row
inherits information from its neighbour in time. For a real detector they would be computed
from the last message the detector saw, which is fine -- but it means rows are NOT independent
samples, and a random split would let a row sit next to its own neighbours in training.

2.7  Train.csv and Test.csv are the same recording
--------------------------------------------------
This is the most important fact about the dataset. Step 1 audits it:

  * All 1,094 (time, class) pairs in Test.csv also appear in Train.csv (100%). The class
    counts are identical.
  * 48 of the 52 feature columns are IDENTICAL value-for-value. Only the four timing columns
    differ: timeLastMsg in 69% of rows, stDiff in 68%, sqDiff in 65%, recentChange in 56%.
  * 255 rows (23%) are identical in every single column.
  * Train.csv's timing columns can be rebuilt from its own time-ordered rows (97-99%);
    Test.csv's cannot (31-35%). Test.csv's timing columns were therefore derived by some other
    ordering or process that I cannot see from the files.

So "train on Train.csv, test on Test.csv" is not testing on new data: it asks the model to
recognise messages it has already seen, with four columns changed. The audit merges on
(time, class) rather than time alone -- merging on time alone would fake column differences.

2.8  What this means for how the project evaluates
---------------------------------------------------
Three ways to score the same model (macro-F1, outputs/step3_protocols.csv, your run):

                        all 52     station 20    process 32
  shuffled rows CV       0.789       0.811         0.284    (neighbouring copies on both sides)
  BLOCKED time CV        0.714       0.723         0.308    <- the honest number used everywhere
   (SD over folds)      +/-0.029    +/-0.031      +/-0.019
  Train -> Test          0.987       0.982         1.000    (memorising the same recording)
  Test -> Train          0.461       0.469         1.000

  * The 0.987 is not a result. It is the inflation caused by the leak: +0.273 over the honest
    number. The process view's 1.000 (and 1.000 the other way round) is the clearest sign of
    memorisation: the angle columns are unique per message and identical in both files, so a
    lookup works perfectly; yet by honest evaluation they classify almost nothing (0.308).
  * Shuffled CV (0.789) is also inflated (+0.074 for "all") because a message's neighbours,
    which are near-duplicates, sit in training.
  * Therefore NO number reported anywhere in the project uses Test.csv. The project uses
    blocked time CV inside Train.csv, and a forward test (step 8).

2.9  What the data can and cannot tell us
-----------------------------------------
  CAN     how well each layer's evidence separates the five classes at a message level; which
          features matter; how fast a model scores; what alert threshold gives what false-alert
          budget; how well a detector generalises to a held-out period or attack type.
  CANNOT  anything about grid topology, geography, line capacity or other substations: it is
          ONE testbed substation, ~8 minutes, one capture. It says nothing about how a
          detector sees an attack that spans several substations, nothing about time-to-first-
          alert (there are no attack "episodes" with start and end), and its Injection and
          Replay classes have only ~100 messages each, so their recalls are noisy (+/-0.12 to
          0.16 SD across folds).
  That is why step 5 and 7 simulate the grid, and why the link between data and grid is kept
  to ONE clearly-labelled place: the measured recall of each detector tier.

~~~ E6 - OPERATING POINT AND ALARM BUDGET  (what threshold does each tier ship with?) ~~~
Trains / tests  YES. A 5-class model gives each message an out-of-fold attack score
                P(Masquerade)+P(Injection)+P(Replay) ("out-of-fold" = scored by a model that never

~~~ E8 - UNSEEN-ATTACK GENERALISATION  (does one central model fit every site?) ~~~
Question        If a detector is trained where attack type A was seen and deployed where a new
                variant B appears, does it still raise the alarm?
Trains / tests  YES. Leave-one-attack-class-out: for each attack class, train a detector
                WITHOUT any message of that class ("unseen") and one WITH it ("seen"), inside
                the same blocked folds, and compare how many of that class they catch at the

------------------------------------------------------------------------------------------
STEP 5   step5_design_grid.py   -   BUILD a grid from scratch with graph algorithms
------------------------------------------------------------------------------------------
Question   Instead of fitting models to a grid somebody already laid out, can we CREATE the
           grid -- lines, sensors, zones, hubs, control centre -- and let the number of levels
           fall out of the result?
Trains / tests   nothing is trained. It reads the numbers steps 1-4 measured (message rate,
                 merging units per row, feature counts, inference latencies, detection rates),
                 builds a grid, and stress-tests it with graph traversals. Every input prints
                 its provenance (measured / FALLBACK / STALE); with --require-measured it
                 refuses to run on anything that is not fresh.

The five stages (the algorithms are explained in PART 5)
  A  power.py          lines          Kruskal minimum spanning tree, then greedy augmentation
                                      guided by Tarjan bridge / cut-vertex detection, until the
                                      grid is N-1 secure.
  B  observability.py  PMUs           minimum dominating set, solved exactly by an integer
                                      program, with the zero-injection-bus propagation rule.
  C  hierarchy.py      zones/hubs/CC  all-pairs Dijkstra, k-medoid (PAM) zoning, the smallest
                                      number of zones that meets every constraint.
  D  security.py       stress tests   BFS failure sweeps, lateral-movement BFS, max-flow path
                                      diversity.
  E  evaluate.py       numbers        traffic per link, latency, cost, the A/B/B+/C comparison,
                                      and the role -> model table.

Result for the default setting (40 substations, seed 42; the design is deterministic, so your
run and the first machine give the same grid):

  * LINES: 47 lines, 2,031.8 km. A radial tree needs 39; the 8 extra lines remove every single
    point of failure. Cost +30.1% over the tree and 77.4% below a full mesh (142 lines).
        variant          lines  bridges  cut vertices  worst 1-node outage strands  diameter
        radial (MST)       39      39         29              21 substations           22 hops
        designed           47       0          0               0                       13 hops
        full mesh         142       0          0               0                        6 hops
  * PMUs: 12 (30% of substations), found exactly by an integer program that also uses the
    zero-injection rule. Plain greedy needs 13, and so does the exact solution without the
    zero-injection rule. (outputs/step5_pmu_curve.csv shows the greedy build-up: 97.5% of
    substations observed with 12 PMUs, 100% with 13.)
  * ZONES: the sweep over the number of zones k is in outputs/step5_k_sweep.csv:
        k   largest zone share   hops   verdict
        1        100%             9     violates share and hops (one hub = whole grid)
        2        59.5%            6     violates
        3        34.9%            5     violates
        4        30.2%            4     violates (share)
        5        25.4%            3     violates (share just over the 25% cap)
        6        24.6%            3     FEASIBLE  <- chosen

    wires are the money.

    detection, and losing one PMU changes nothing. PMUs are needed for state estimation

     false-alert budget, so keeping it fixed would understate the spread). 41 Fault and 100
     Replay messages are few, so the intervals matter.

##########################################################################################
PART 5   STEP 5 IN DEPTH: BUILDING A GRID WITH GRAPH ALGORITHMS
##########################################################################################
All of this lives in src/design/. A graph here is: nodes = substations, edges = transmission
lines. Fibre-optic communication rides on the same corridors, so the communication graph has the
same shape as the power graph (edge latency = length x 5 microseconds per km + 0.1 ms per hop).

5.0  The sites (sites.py)
-------------------------
40 sites are scattered at random in a 300 km square (side grows with the square root of the
count so density stays constant), with a minimum spacing so substations do not stack. 20% are
generators, 20% are "junctions" with no generation and no load (zero-injection), the rest are
loads; total generation is scaled to 120% of load. A seed makes it reproducible. You can instead
supply your own sites in a CSV (id,x_km,y_km,kind,mw). Costs: lines 1,500 kUSD/km (assumed).

5.1  Stage A - the lines: minimum spanning tree, then repair weak points (power.py)
-----------------------------------------------------------------------------------
Goal: connect all sites so that no single line or substation outage splits the grid, as cheaply
as possible. The exact problem ("survivable network design") is NP-hard, so the code uses the
classic two-phase heuristic.

 Phase 1 - Kruskal's MST (the cheapest connected backbone).
   1. List every pair of sites with its length in km.
   2. Sort them shortest first.
   3. Walk the list; accept a pair only if its two ends are not yet connected (checked with a
      union-find structure); otherwise it would close a loop and is skipped.
   4. Stop with n-1 = 39 lines. This is a TREE: cheapest, but "radial": every line is a bridge
      and every interior substation a cut vertex.

 Phase 2 - greedy augmentation guided by Tarjan's low-link search.
   1. Find the weak points: BRIDGES (lines whose loss splits the grid) and CUT VERTICES
      (substations whose loss splits it). One depth-first search (iterative, so no recursion
      limit) gives each node a discovery time disc[u] and a low[u] = the earliest discovery time
      reachable from u's subtree using at most one back-edge. Line (p,u) is a bridge iff
      low[u] > disc[p]; a non-root p is a cut vertex iff low[u] >= disc[p] for some child u (the
      root is one iff it has 2+ children).
   2. A candidate line (u,v) REPAIRS a weak point iff u and v lie on different sides of it
      (BFS/DFS labels the sides).
   3. Among the candidates (the MST edges plus each site's 6 nearest neighbours) add the one
      that repairs the most weak points PER KILOMETRE (ties: the shorter). Repeat until no weak
      point is left. If the candidate pool cannot finish the job, widen it to every pair.
   Result: 8 lines added, 47 in total, zero bridges and zero cut vertices.

 A tiny example:      A--B--C--D        a path: 3 bridges, B and C are cut vertices
                      add D--A          a ring: no bridge, no cut vertex -> N-1 secure
 One extra line fixed everything because it joined the two ends. In a real network the greedy
 rule chooses short lines that close the most loops.

 What "N-1 secure" means HERE: the grid stays CONNECTED after losing any one line or any one
 substation. It does NOT check that the surviving lines can carry the rerouted power (that needs a
 power-flow model). Say so in your report (PART 8).

5.2  Stage B - where the PMUs go: a dominating-set integer program (observability.py)
--------------------------------------------------------------------------------------
Fact: a PMU at substation p measures its own bus and every line leaving it, so p AND all its
neighbours become observable. We want every substation observable with the fewest PMUs.
 * Formulation: binary x[v] = 1 if v gets a PMU. Minimise the sum of x subject to: for every
   substation u, the sum of x over u and its neighbours >= 1 (k-fold redundancy: >= k). That is a
   minimum DOMINATING SET.
 * Solver: scipy.optimize.milp (HiGHS), exact and deterministic. Without scipy a greedy
   algorithm plus reverse-delete is used; both answers are reported so the greedy gap is visible
   (greedy: 13).
 * Zero-injection rule: at a junction substation z (no generation, no load), Kirchhoff's current
   law says the currents sum to zero. So if all but ONE member of z's closed neighbourhood are
   observed, the last one is deduced. This spreads like a BFS fixpoint and lets the program remove
   a PMU after re-verifying that full observability still holds. 13 -> 12 PMUs (30%).
 * k=2 (every substation seen by two PMUs, so one PMU can fail) needs 25 PMUs.
 Caveat: the data cannot say whether detection stays as good on a bus observed only by
 inference. E1 only shows the phasors do not matter for detection at all.

5.3  Stage C - zones, hubs and the control centre (hierarchy.py)
-----------------------------------------------------------------
Every substation always hosts a station correlator. The question is whether HUBS are needed
between stations and the control centre (CC), how many, and where.
 1. All-pairs shortest latency: Dijkstra from every node gives the latency matrix D.
 2. For k = 1, 2, ..., 12 zones: choose k hub sites by PAM k-medoid clustering (a facility-
    location heuristic): start greedily, then repeatedly SWAP a hub with a non-hub if that lowers
    the bay-weighted total latency to the nearest hub; 6 random restarts.
 3. The zones are the cells of a multi-source Dijkstra from the hubs. Because each node inherits
    its cell from its parent in the shortest-path tree, every zone is CONNECTED by construction:
    its members can reach their hub without leaving the zone (tested on 20 random graphs).
 4. Check the constraints for that k:
      blast radius   no hub fronts more than 25% of all bays            (policy, assumed)
      hops           evidence travels at most 4 hops to its hub
      zone size      a zone has at least 3 stations (enough to fuse across)
      latency        bay -> hub verdict <= 1,000 ms; -> CC verdict <= 10,000 ms
      compute        a node needs <= 70% of 8 cores
 5. Pick the SMALLEST k that satisfies all (cost rises with k). The whole sweep is saved, so the
    report can show which constraint forced each extra zone and which were slack.
 6. The CC goes on a non-hub substation (the one with the smallest bay-weighted latency to the
    hubs) so a single failure never removes two roles. With k = 1 the hub and CC are the same
    node, giving 3 levels instead of 4.
 Latency model (milliseconds):
    bay -> hub verdict = wait for the next message (1000/2.294 = 436)
                         + sentinel p95 + station p95 + hub p95   (the three scorings, from E4)
                         + 0.2 (local network) + worst station-to-hub network latency
    bay -> CC verdict  = the above + worst hub-to-CC latency + one more p95 scoring
 Compute: cores needed = bays served x message rate x per-message scoring cost / utilisation cap,
 where the cost is E4's batch figure. At 2.3 messages/s it is ~0.00 cores everywhere.

5.4  Stage D - stress tests are all traversals (security.py)
-------------------------------------------------------------
 * FAILURE SWEEPS (BFS on "the graph minus the failed nodes"). For each failure, a BFS from the
   control centre (and one from each hub) finds which stations can still deliver an alert.
   One sweep deletes each substation in turn; the other deletes everything within 50 km of each
   substation (a storm or a coordinated attack: fibre rides the same towers).
   Four views are scored: central (needs the CC), central + backup CC, tiered fused (reach hub
   or CC), tiered any-level (local detection, which is 1.0 by construction).
 * LATERAL MOVEMENT (BFS from a compromised node). On a flat network all links are usable; on
   the zoned network only links inside a zone are. The share of bays reached is the intruder's
   range: 100% flat vs mean 18.6% / max 24.6% zoned.
 * PATH DIVERSITY (maximum flow). Menger's theorem: the number of independent routes between two
   nodes equals the smallest number of nodes whose loss separates them. Computed by Edmonds-Karp
   max-flow on a graph where every substation is split into an "in" and an "out" node joined by a
   capacity-1 arc. Result: every substation has >= 2 vertex-disjoint routes to the CC.
 * BACKUP CONTROL CENTRE for the centralised baselines: the bay-weighted median site at least a
   minimum distance from the primary. Included so the centralised designs are not a straw man.

5.5  Stage E - turning the design into the numbers an architecture review asks for (evaluate.py)
------------------------------------------------------------------------------------------------
 * Traffic is routed along shortest-latency trees and summed per link, so "bandwidth" is a per-
   corridor load, not one aggregate. Per bay: evidence vector 13.8 bytes/s (6 features) vs raw
   119 bytes/s (52 features) vs phasors only 73 bytes/s.
 * Costs: lines, fibre, sensors, computers (all assumed prices).
 * The A / B / B+ / C comparison (PART 4 step 5) and the role -> model table.

5.6  The hand-written graph library (graph.py)
-----------------------------------------------
BFS, DFS components, Tarjan bridges/cut vertices, multi-source Dijkstra, Kruskal with union-find,
Edmonds-Karp max-flow, minimum vertex cut. Written by hand so each design decision can name the
traversal that made it, and so the project needs no extra dependency. tests/test_graph.py checks
every routine against networkx on random graphs when networkx is installed (pip install
networkx; five tests are skipped otherwise).


##########################################################################################
PART 6   DEFAULT GRID VERSUS OPTIMIZED GRID: HOW THE VERDICT IS REACHED
##########################################################################################

6.1  Why a rule fixed in advance
--------------------------------
A comparison where the author may pick the yardstick afterwards proves nothing. So the rules
below were written BEFORE the results were looked at, are printed together with the results, and
are included in the unit tests. A rule that cannot say "no" is not evidence; section 6.5 shows
this one can.

6.2  The outcome of one metric
------------------------------
For every metric the code computes the difference (optimized minus default) and a 95% interval
for it. The metric has a TOLERANCE: the smallest difference that matters.
   * "optimized better" (or "worse") only if the WHOLE interval lies beyond the tolerance;
   * "tie" if the whole interval lies inside plus-or-minus the tolerance;
   * "inconclusive" otherwise (the interval straddles the tolerance).
Tolerances: detection coverage 0.01; latency 10 ms (1% of the 1,000 ms tier-2 budget); link
utilisation 0.01 of capacity; single points of failure 0.5; blast radius and lateral reach 0.02;
independent routes 0.5; price 5% (relative).
The interval is a PAIRED TWO-LEVEL bootstrap: layouts are resampled with replacement (the spread
between synthetic grids) crossed with the 300 detector-recall replicates (the spread in the
measured data), and both grids are scored on the same resamples.

6.3  Two kinds of security metric (and why it matters)
-------------------------------------------------------
 * OBJECTIVES are what the design algorithms minimise directly: bridges and cut vertices, zone
   share, routes to the CC. Beating the default on them shows the algorithm WORKED; it does not
   show the grid is safer.
 * OUTCOMES are what the design never optimised: how much attack detection SURVIVES a failure
   (one lost, regional, random double, adversary's double, worst case).
Only outcomes can establish "better".

6.4  The overall label
-----------------------
   OPTIMIZED BETTER    >= 1 security OUTCOME win, 0 security losses (either kind), 0
                       performance losses. Labelled "(narrow)" unless most outcomes are clear wins.
   NOT ESTABLISHED     otherwise, and the reasons are listed.
Price is never netted against security (a higher price does not veto a win, and a security gain
is not "bought" with a lower price); it is reported next to the verdict with its percentage.

6.5  Evidence that the rule can say no
---------------------------------------
Every run executes a self-check (outputs/step7_summary.json):
   optimized graded against ITSELF          -> NOT ESTABLISHED (all 14 metrics tie)
   roles SWAPPED (naive plays "optimized")  -> NOT ESTABLISHED (10 metrics say the default is better)
A rule that returned "better" in either case would be broken.

and the label was OPTIMIZED BETTER.

Why: the centralised design scores a message ONCE (at the control centre); the tiered design
scores it at the sentinel, the station and the hub. The extra cost is (sentinel p95 + station p95)
minus the network time the zones save (about 4 ms here):
      your laptop      4.90 + 10.50 - 4.0  =  about 11.4 ms
      first machine    2.92 +  5.69 - 4.0  =  about  4.6 ms
So the verdict flips when the two extra scorings together exceed roughly 14 ms, which depends on
the CPU that ran step 4. The same effect explains the by-size results: at 80 substations the
centralised path is longer (more network time), the tiered path saves more, and the label is
OPTIMIZED BETTER again even on your laptop; at 20 and 40 it is NOT ESTABLISHED.
   by size (your run)         naive              budget-matched     control
      20 sites                NOT ESTABLISHED    NOT ESTABLISHED    OPTIMIZED BETTER (narrow)

What this means, honestly:
   * The security result does not depend on the CPU. Every one of the 10 security metrics is a

   * The performance cost is real but small: 11 ms on a path of about 460 ms (2.5%), of which

   * The label "NOT ESTABLISHED" is the pre-set rule doing exactly what it was built to do.

7.2  The two commands, and what "smoke" means
---------------------------------------------
    python run_pipeline.py --smoke     ~2 minutes. Rehearsal: does every step RUN?
    python run_pipeline.py             ~13 minutes on your laptop. The real run.
BOTH of them train and test models. The difference is size, not purpose: --smoke uses 3 folds,
40 trees, 60 bootstrap replicates and 3 layout seeds, writes to outputs_smoke/ and models_smoke/,
and its numbers are never reportable (e.g. blocked-CV macro-F1 0.76 instead of 0.71). A run is
flagged "reportable" only when it is the whole pipeline with default settings and no overrides.
Where the training and testing happens:
    steps 3-4 (blocked CV)   5 models per experiment, one per fold; tested on the unseen blocks
    step 6                   the three final detectors; out-of-fold scores set the thresholds
    step 8                   one model on blocks 0-13, tested once on blocks 15-19
    steps 1, 2, 5, 7         train nothing (profile, layers, grid design, grid comparison)
Useful variations
    python run_pipeline.py --only 4 6 8          just the train/test steps (names work too)
    python run_pipeline.py --skip 3
    python run_pipeline.py --extras              also the slow sensitivity and scaling sweeps
    python run_pipeline.py --keep-going          do not stop at the first failing step
    python run_pipeline.py --name "600 trees" --note "after changing max_depth"
Settings can be overridden without editing config.py through environment variables
(PP_N_ESTIMATORS, PP_N_SPLITS, PP_BOOTSTRAP_B, PP_ENSEMBLE_SEEDS, PP_OUTPUT_DIR, PP_MODELS_DIR).
They are written into the run record, and any override makes the run non-reportable.

PART 8   LIMITS AND HONEST CAVEATS
##########################################################################################

8.1  About the data
-------------------
 * 1,094 messages from one ~8-minute capture of one testbed. Injection and Replay have ~100
   messages each; their recalls carry +/-0.12 to 0.16 SD across folds, Fault (41 messages) is
   noisier still.
 * Train.csv and Test.csv are one recording, so there is no independent test set. The forward test
   is the nearest substitute and it is a single split.
 * Rows are not independent (the timing columns are differences with the previous row), which is
   why splitting is by time block.
 * No attack episodes: attacks are interleaved messages, so there is no "time to first alert".
 * The meaning of derived columns (consistency, Cs, the MU*Cs flags) is my reading, not
   documentation from the dataset's authors; I could not open the Kaggle page.

8.2  About the grid work
------------------------
 * COSTS, DELAYS AND POLICIES ARE ASSUMED, not measured: line price, PMU price, 25% blast cap,
   50 km outage radius, per-hop delay, minimum zone size. They are all in config.GRID_ASSUMPTIONS.
   The sensitivity sweeps show which conclusions survive changing them; the cost numbers
   themselves are only relative.
 * N-1 IS TOPOLOGICAL: the grid stays connected. Whether the surviving lines can carry the
   rerouted power needs a power-flow model, which is outside this project.
 * Grids are SYNTHETIC (random sites) or SCHEMATIC (the 7 standard cases have layout coordinates,
   not geography). Every kilometre-based quantity is relative.
 * One testbed substation's recall is used for every substation. Cross-substation fusion (which
   would help the tiered design) is deliberately not credited.
 * The adversary is a scenario set (worst pairs among a pool), not a threat model.
 * The default grids are one reasonable reading of "not optimized". The budget-matched default and
   the control exist so the result is not an artefact of a weak baseline.
 * The detection results (recall, false alerts) come from one substation's message-level data;
   the grid-level coverage numbers are therefore a model of the system, not a measurement of one.
 * The tiered design is slower by the cost of two extra scorings (PART 6.6).

PART 10   QUESTIONS YOU MAY BE ASKED, WITH ANSWERS
##########################################################################################

Q1  Why not just train on Train.csv and test on Test.csv?
A   They are the same recording: every (time, class) message in Test is in Train, 48 of 52
    columns are identical, and 23% of rows are identical in every column. That split measures
    memorisation (0.987); the honest number is 0.714.

Q2  Why macro-F1 and not accuracy?
A   "Normal" is 41.6% of the data, so predicting Normal always is 41.6% accurate. Macro-F1 gives
    each class equal weight, so missing Fault (41 messages) or Replay (100) is visible.

Q3  Which evidence matters, and what did you learn?
A   The station layers (GOOSE state and timing, consistency checks, relay flags). Together they
    reach 0.723; the raw phasors alone reach 0.308 and add nothing to the station layers.
    Masquerade and Fault are easy (93-94%); Injection and Replay are hard (~40%).

Q4  Why are Injection and Replay hard?
A   A replayed message is a genuine old message, so it looks Normal on most columns
    (consistency 0.84, breaker state 0.12). Injection mixes both patterns (50/50). Only subtle
    timing/counter patterns separate them, and there are only ~100 examples of each.

Q5  How is the optimized grid created?
A   Kruskal MST for the cheapest backbone; then greedy line additions guided by Tarjan's
    bridge/cut-vertex search until nothing is a single point of failure; PMUs by an exact
    dominating-set integer program with the zero-injection rule; zones by k-medoid on shortest-
    path latency, taking the smallest k that meets the blast-radius, hop, size, latency and
    compute limits; stress tests by BFS, and independent routes by max-flow (Menger).

Q6  How do you know it is N-1 secure?
A   The Tarjan search finds no bridge and no cut vertex (also unit-tested for many seeds and sizes).
    It is topological: it proves the grid stays connected, not that the lines can carry the power.

Q7  Why four levels?
A   Because a hub may expose at most 25% of the bays. One zone would expose 100%; the smallest
    number of zones that meets every constraint is 6, which gives sentinel, station, hub and
    control centre. With a looser policy (k=1) you would get three levels. It is an output.

Q8  Why is the optimized grid "better"?
A   On security, clearly: it keeps 0.44 of attack coverage in the worst failure scenario (defaults:
    0), has 0 single points of failure (79 / 48), 22.5% blast radius (100%), and two independent
    routes everywhere (one). On performance it ties, apart from ~11 ms extra latency on your hardware.

Q9  Isn't it just because it spends more?
A   No: the budget-matched default spends the same on extra lines (but untargeted) and still keeps
    0 in the worst case and has 48 single points of failure.

Q10 Isn't it just the tiered detection?
A   Largely yes for the worst-case coverage: tiered detection on the cheapest tree already gives
    0.409. The designed lines add the removal of every single point of failure, two routes
    everywhere and the edge against an adaptive adversary (0.504 -> 0.533). PART 6.7.

Q11 Why does your laptop say NOT ESTABLISHED?
A   The tiered design adds two extra model scorings; on your CPU they cost 15.4 ms against ~4 ms of
    network saving, a net +11.4 ms, over the 10 ms tolerance fixed in advance. All security metrics
    still win. On faster hardware or larger grids the label is OPTIMIZED BETTER. PART 6.6.

Q12 What is measured and what is simulated?
A   Measured: detector recall, feature counts, message rate, inference latency. Simulated: the
    grids, failures and delivery of alerts. Assumed: prices, policies, delays.

Q13 Why synthetic grids? What about real ones?
A   The Kaggle data has no topology. 90 random layouts give a distribution; the 7 standard test
    cases (IEEE 14-300, Illinois 200) show the same pattern on real topologies, with schematic
    coordinates.

Q14 Is a 1% false-alert budget realistic?
A   It is about 725 alerts per day on this testbed. E6 shows the trade-off: ~2,000/day buys 78% recall,
    ~10,000/day 89%. The data cannot test budgets below ~181/day (one false alert).

Q15 What would you do with more data?
A   Several substations and longer captures with real attack episodes; measure cross-substation
    fusion gain and time-to-first-alert; add a power-flow check to N-1.

Q16 Is --smoke the training and the full run the testing?
A   No. Both train and test. Smoke is a small, fast rehearsal whose numbers are not reportable.

Q17 Where does each number in the report come from?
A   See the file guide below.
